How a change ships
  1. Built. An agent writes the change on its own branch and runs the project's own checks (for this project: pytest and ruff) before saying it's done.
  2. PR. Mahler (not the agent) pushes the branch and opens a pull request: the proposed change, waiting to be merged.
  3. CI checks. GitHub runs the project's automated tests on the PR. Green means they all passed. Red: Mahler first retries once if it looks like a flaky test, then starts a fix run with the failure log. If the fix limit runs out, the change is parked and shows under Blocked.
  4. Review. A different AI platform from the one that built it reads the change. Problems it finds go back for a fix, then through checks again.
  5. Merged. On green checks and a clean review, Mahler merges it into main and closes the issue. No one has to press a button.
  6. Confirmed live. Where a project has an automatic post-merge check, a pass marks it verified. Otherwise it counts as done after 14 quiet days with no problem reported.
